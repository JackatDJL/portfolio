# Private application signatures

The application PDF exporter remains the only rendering/composition pipeline. Electronic signatures apply only to a frozen, complete composite, after cover letter, freshly resolved private CV and ordered attachments have been composed. A separate optional handwritten graphic is rendered by the shared LuaLaTeX pipeline in the letter and CV; it is not a cryptographic signature or QES.

The same encrypted handwritten source may be enabled for standalone private CV PDFs and authorized CV pages through **Globals → Lebenslauf → Unterschrift**. Delivery requires a current profile-scoped CV session and rechecks grant expiry/revocation on every image request. The private CV page adds configured print place/date and the typed name only after the authorized image loads. Public CV pages can show an independently generated synthetic line motif instead; it never uses real signature pixels or strokes.

The motif's fine-line, rosette and guilloche-like forms borrow only the visual language of security printing. The [ICAO Doc 9303 security specifications](https://www.icao.int/publications/Documents/9303_p7_cons_en.pdf) describe guilloche backgrounds alongside physical substrate, ink and other security measures; the [Bundesdruckerei glossary](https://www.bundesdruckerei.de/de/glossar) likewise discusses printed line motifs as one part of document security. This software renders ordinary SVG paths: it has no UV response, secure substrate, authenticity check, identity assurance or copy prevention. It is decoration only and must not be presented as a passport feature or security control.

## Operator workflow

1. Install `requirements-pdf.txt` in the existing private PDF Python environment and run the new Laravel migration through the normal deployment procedure. No production migration is performed by this PR.
2. Save the application, check its complete unsigned preview, then choose **Endgültige PDF einfrieren** in the Statamic application editor. Download that version's unsigned original.
3. Sign that exact file externally. Use incremental PAdES signing, without rewriting, printing, flattening, editing or merging it. The importer deliberately rejects broader changes. Existing embedded signatures and application forms are unsupported at preparation time; resolve these before paying a signing provider.
4. Select the signed PDF beside that same version and import it. Import does not activate delivery. Validation runs locally, with certificate URL fetching disabled. Invalid signatures, mismatched originals, unsafe incremental modifications and non-signature field changes are rejected.
5. Review the separate integrity, certificate-path and qualification results. Explicitly select the version for delivery only after assessing those limitations. Preview always generates the current unsigned PDF; canonical export/recipient delivery uses the selected signed version. Changed application/CV/documents cause a digest mismatch and block signed delivery; there is no silent unsigned fallback. Explicitly select unsigned delivery or prepare/sign a new version.

Unsigned mode is the default. Archived versions remain available privately and are not overwritten. A valid signature with an untrusted certificate can be archived and explicitly selected; the system does not claim the signer identity or QES has been established. Recipient links retain the existing application-specific authorization and revocation checks; they do not grant access to signature administration or archive downloads.

## Validation scope

`SignatureValidator` is independent of `SignatureProvider`. The supplied pyHanko adapter validates the cryptographic signature, coverage and conservative incremental-update policy against the exact frozen bytes. Original prefix matching alone is insufficient: a later revision can replace page content. Changes to signed artifacts are never repaired or normalized after signing.

**This implementation never verifies QES qualification.** It does not consult EU trusted lists, establish qualified certificate/QSCD status, establish a legally reliable signing time or check online revocation. Certificate trust defaults to untrusted. `APPLICATION_SIGNATURE_TRUST_ROOTS` may point to an administrator-managed PEM trust bundle; pinning a self-signed certificate establishes neither QES nor legal identity. Offline soft-fail trust evaluation must not be interpreted as confirmed non-revocation. Signature metadata reports `qualification=not_assessed`, `qes_verified=false`, `revocation=not_checked_offline` and `long_term_validation=not_assessed_offline` explicitly.

LTV, LT/LTA augmentation and archival renewal require a separate validator/post-processing implementation with controlled trust lists, revocation evidence and qualified timestamps. DSS is a possible future validation adapter, not an identity provider or signing credential. Do not upload personal documents to public DSS demos. Any future augmentation must create a separate version and revalidate it; never mutate the retained unsigned/signed originals.

## Provider extension and sandbox

`SignatureProvider` exposes explicit availability, remote-signing, QES, sandbox, upload/hash and LTV capabilities. No live provider adapter is enabled: the [official-source comparison](application-signature-provider-research.md) did not establish an accessible, affordable private-individual API or eligibility at age 17. Unsupported provider configuration fails closed. Future adapters must use server-side secrets, have explicit exact-digest authorization, idempotency and reconciliation for ambiguous remote outcomes, and separate initiation, user authentication and completion. Do not reuse the sandbox's synchronous workflow for paid asynchronous requests.

Default `APPLICATION_SIGNATURE_PROVIDER=unavailable` makes no provider requests. For local/testing only, set `APPLICATION_SIGNATURE_PROVIDER=sandbox` and `APPLICATION_SIGNATURE_SANDBOX=true`. The CP offers a separately confirmed local test action. It generates a disposable in-memory self-signed certificate, makes no network/paid requests and stores no signing key. Sandbox artifacts are visibly marked **not QES** and cannot be delivered through recipient access. Production rejects sandbox even when configuration enables it. External imports are evaluated by signature evidence, not by provenance labels or scanned appearance.

Preview, export, save, autosave and recipient access never initiate signing. There is no email sender. Existing `ApplicationPdfPostProcessor` remains unchanged; signing is explicitly outside rendering/cache generation.

## Privacy and operations

External-signature artifacts live beneath `storage/app/private/application-signatures`, with opaque application hashes, UUID version directories, 0700 directories and 0600 PDF files. The reusable handwritten source is stored separately as Laravel-encrypted data beneath `storage/app/private/application-handwritten-signature`; its temporary PNG is created only in a 0700 export work directory and deleted after rendering. No signature bytes or strokes enter public assets, Statamic content, content sync or Git. Verification metadata is Laravel-encrypted in the database; retain `APP_KEY` securely with encrypted backups. Checksums detect changed/missing files before use. CP endpoints require a Statamic super user and normal CSRF protection for mutations; responses use private/no-store and noindex headers. Parser errors are sanitized. Configure PHP/web-server upload limits consistently with the 100 MiB server validation limit and keep the parser environment patched.

Private storage permissions are defense in depth, not protection against a compromised server/admin or a public web-server alias. Do not expose this directory through any asset container or symlink. Retain only necessary applications and verification records; backups and archive retention need an operator policy. No automated deletion or public publication is implemented. A visible handwritten/scanned signature can be copied; no copy-prevention claim is made. The public SVG pattern never overlays, blurs, transforms or derives from the genuine private signature. It overlays only the separately configured public example or the font name.

At age 17, provider contract eligibility and legal consent remain unresolved. Do not equate availability of German online eID from age 16 with eligibility for a particular QES service or binding contract. Obtain provider confirmation and any required guardian consent before using a paid service. The research document distinguishes verified provider terms from unknowns. This software and its status labels are not a legal opinion on a particular application or signature.

### Placement, typography and public artwork

CV signature blocks sit in the main content column after the last section, in both HTML and LuaLaTeX. The order is location/date, signature, and a normally typeset sender name. Typed mode uses the locally bundled OFL-licensed Momo Signature font in the same slot as a graphical signature. Width, baseline and alignment remain application settings; graphical mode continues to use the encrypted private source.

In **Globals → Lebenslauf → Unterschrift**, the public block offers either the name in Momo Signature or an independently uploaded/drawn example. Its editor reuses the existing CP controls but saves to a separate encrypted source under `storage/app/private/public-signature-example`; it never reads or falls back to the genuine source. Upload only an obviously fictional example. Selecting and enabling this public variant intentionally makes its raster image available through `/cv/signature-example`; disabling it removes delivery. Source strokes remain CP-only. The private editor remains under **Bewerbungsvorgaben → Handschrift**, linked from the CV settings.

The public overlay consists of twenty independently regenerated thick line layers, offset by up to 10 CSS pixels in either direction, with gamma, color and blend effects. Reduced-motion preferences disable regeneration; printing pauses it. These are decorative effects. They cannot prevent copying, extraction or screenshots and provide no reliable attribution. This explanation belongs in administration/documentation, not as a caption on the CV.

### Detail-page return links

Internal experience, education, project and publication links carry a non-secret `cv_return` path. Only a public CV path or an application CV path authorized in the current session is accepted; arbitrary hosts, query strings and fragments are rejected. Each browser tab keeps its own explicit context. Detail URLs with this context are excluded from Statamic static caching and receive private/no-store/noindex response headers. Returning to a CV uses its existing exact-path session grant, with expiry and revocation still checked. Visiting `/cv` does not authorize it using another profile's grant.

Ordinary authorized CV PDFs retain the existing CV capability fragment on internal detail links. The detail page exchanges that fragment for the exact profile session, then immediately removes it from the address bar. Bearer secrets never enter query strings. Application PDFs instead use `/applications/{id}/cv` and the existing authorized application session (or a logged-in superuser), preserving application overlays without exposing CV or application tokens in the PDF. Their HTML view, private-data/signature requests and PDF route recheck that application grant. The application private-data payload allowlists only the contact and signature fields used by those views; birth date and birthplace remain outside this application delivery scope. Opening the PDF in a different browser does not authorize that browser; the recipient must first open their separately delivered recipient link there.
